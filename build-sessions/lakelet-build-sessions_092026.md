## 12. Overture's geometry column refused every read (2026-09-21; `core/lakelet/engine.py`, `dbt/plugin.py`)

Hants: `select * from place limit 10` on the demo project failed with "failed to cast column geometry from GEOMETRY('OGC:CRS84') to BLOB". Two probes on the Mac (a temp project, the first Overture file) found it. The file is not a native Parquet GEOMETRY type: it is `BYTE_ARRAY` with a GeoParquet `geo` footer entry, which attach registers as `binary` (right). DuckDB's `enable_geoparquet_conversion`, on by default, turns such a column into GEOMETRY *when the spatial extension is on the machine* — it is on Hants' Mac, not in the container, which is why the suite never saw it — and the Iceberg scan then has to cast GEOMETRY to the catalog's binary, a cast that does not exist even with spatial loaded. The engine and dbt's connection now `SET enable_geoparquet_conversion = false`: the WKB bytes come through as the catalog says, and `st_geomfromwkb`/`st_astext`/`st_aswkb` are core functions in DuckDB 1.5 for anyone who wants the geometry. `test_a_geoparquet_column_reads_as_the_binary_the_catalog_says` (Moto; a DuckDB-written GeoParquet prefix) pins it; `/docs/remote`'s Overture section says so. The probe also tried the format-version 3 route (an Iceberg `geometry` column): pyiceberg 0.12 refuses to write V3 metadata, recorded against V1 in `TASKS.md`, with the catalog's bare-500 answer as a small open item. With the rows back, the grid showed the geometry as `{"0":1,"1":1,…}` — `JSON.stringify` of a `Uint8Array`; a binary cell is now its size and first eight bytes in hex (`21 bytes · 0101000000000000…`), pinned in `Grid.test.tsx`.
