## 1. The research

Three new articles read alongside the four of 2026-09-15 (`research/README.md` has those; its rows for these three are pending the decisions file):

- **Amina Okanovic, "DuckLake didn't fix Iceberg's metadata bottleneck. It moved it into a single Postgres instance"** (Medium, 2026-09-07). Every format puts its serialization point somewhere: Iceberg on one compare-and-swap of a pointer, DuckLake in a multi-table transaction on a shared database; a Postgres catalog fails on connection count before metadata volume; Quack (DuckDB as an HTTP server, May 2026, folded into 1.5.3) is DuckDB Labs building the multi-writer layer itself. *For us:* Iceberg's bet is right for the team story; our SQLite loopback catalog is her "local dev only" row and the README already says one writer; `remote-catalog-plan.md` R4 (our catalog on Postgres) must be sized for connections.
- **Nazmul Hasan, "I appended 5,000 rows 200 times. Iceberg wrote more metadata than data"** (GoPenAI, 2026-09-10). pyiceberg 0.12, a SQLite catalog, DuckDB 1.5.5, no maintenance: 19.4 MB of metadata for 15 MB of data, 806 files, an 8.2× full-scan slowdown; Delta 0.21 MB and 1.6×; "choosing Iceberg is choosing to operate a maintenance job"; plain Parquet wins for a single appending writer. *For us:* his stack is ours; every `lakelet run` of a `table` model is a commit (delete plus insert on V2); maintenance belongs in the free local product, not the Team tier; the file count is in the metadata the estimator reads, so "needs maintenance" is a verdict; his script is V2's natural gate.
- **Dean J Murphy, "What the heck is Duckle"** (Medium, 2026-09-23). A drag-and-drop ETL canvas over DuckDB, hundreds of connectors, a local Qwen assistant, the workspace as plain JSON; no table format, catalog, versions or dbt; rough edges. *For us:* the non-SQL user (the PRD's P3) is Duckle's for now; Gordon's Renart piece names the wave both belong to.

A name check found **Smith-Cruise/Lakelet** on GitHub: "a single-binary SQL engine for LakeHouse tables", Rust on DataFusion, Apache 2.0, one star, 94 commits, active. Same category. Not a threat; what a trademark search finds first.

## 2. Positioning

The unique thing built is not a lake but the judgment over open tables: **judgment** (the gauge: a verdict from statistics before a run, a refusal, estimate against actual recorded), **memory** (versions, lineage with a state per model, `run --stale`, the Changes feed merging snapshots, runs and commits), **operations** (safe replace, expire, relocate, recovery; compact next). Everything else in the articles is taken or contested: engine, formats, catalog protocol, dbt, the canvas, the IDE. The lede leads with the commodity and ends with the gauge; proposal: flip it. **The name:** "Lakelet" names the storage half. Placeholder **TBD\*** in planning documents from now; Lakelet stays the working name in code and on the site; the deadline is the ship brief's S7 (PyPI, brew, the signing identity, the domain fix the name). A test for a name: it names the judgment, survives bucket, worker and agent, and is free on PyPI, brew, GitHub, a domain and USPTO 9/42.

## 3. The business model, gauge-first

What is sold moves from compute to decisions; burst is one backend the decision can pick. The ladder: Local (free, ever) · Team (seats: one catalog, one history, one gauge record) · Route and cap (seats, plus metered burst; "here 34 min, your Trino 1 min, BigQuery about 24 cents", with the engine's own ceiling set on the job) · Agents (per identity: a daily cap, an audit log, read-only by default) · Platforms · Self-hosted. Open boundary: the estimator, verdicts, record and cost models are Apache 2.0; paid things are things we run or host. Nothing changes N3's order; route-and-cap is a Day 2 brief.

## 4. Does the standalone app still make sense

Yes, as one surface and the on-ramp, not as the product. The verdict already travels with the query (stderr, headers, the DAG). What the window alone does: the analyst's first ten minutes, and a drop that hands the core a path. What a browser tab does as well: every view of the record. Suggested: keep shipping the DMG; have the core serve the same SPA so "never a gate" is true in fact; add no more screens; next surfaces MCP and a Python entry point, then a thin VS Code client.

## 5. Prediction alone is not a product

The loop: estimate, enforce, observe, learn. An estimate nothing executes through has no actuals; without actuals it neither improves nor earns trust; an estimate that cannot cap anything cannot be sold. Five ways through: be the execution path where the tables are ours (local, burst, dispatch with the engine's per-query ceiling; `lakelet run` is the highest-volume capture point); observe where we cannot execute (the engine's query history, matched by a tag, with read-only credentials); split the verdict into fact (bytes and files from the manifests) and forecast (seconds, memory, with a confidence and an "unproven" state); enforce locally now in seconds and bytes, per query and per agent per day; pool the actuals and seed the pool with reference-machine timings.

## 6b. The category, and `marketing/`

Asked whether we had built an open-source warehouse: the half a person needs, yes (tables in a catalog, SQL, managed transformations, snapshots, statistics, lineage, backups, many readers); the half a team needs, no (many writers, users and roles, a service to connect to, unattended runs, compute beyond the machine). The bare phrase "open-source warehouse" is ClickHouse's shelf and loses there. Hedges ("warehouse-like", "extension") keep us off every shelf. The category chosen: **a warehouse for one**, with "on the machine you already own" as the clause that follows; the qualifier expires when the team catalog lands, which is when the product changes. Then the line: *TBD\* is an open-source warehouse for one machine, for SQL and dbt: it says whether a query fits before it runs, records what every run actually did, and keeps every table in Iceberg so any engine can read it.* Tagline: *A warehouse for one.* Two beats: *Know what fits. Know what changed.* (first drafted as "Keep what you find"; Hants caught that saving a query is not unique. What is unique in that beat is the record after the run: a changed table marks what reads it stale, not only a changed file; run only what is stale; runs recorded against their estimate; snapshots, runs and commits in one feed. Save as question stays as the on-ramp sentence, not the headline.) A correction along the way: "a question becomes a tested, versioned model in one click" is the solo analyst's pitch and Renart's move if said to the dbt person; for them the line is that the model they wrote gets a verdict, its checks, a version and a state without leaving their editor. The one deliberate crossing of the editor line is Save as question, for the person with no editor, and it should stay the only one. Auto-commit's default should probably follow how the project began (a box for N3 step 4). `marketing/` holds all of it: the README's rules, `warehouse-for-one.md`, `landing-page.md`, `personas-fit.md`. Then a guidebook deck for the folder: `guidebook.md` (fourteen slides, the source, in git) rendered by `build_guidebook.py` with python-pptx in the site's dark palette to `warehouse-for-one-guidebook.pptx`, gitignored like `deck/`; the app icon as the mark and the README's screenshot on the verdict slide.
